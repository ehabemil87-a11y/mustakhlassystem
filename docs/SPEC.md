# نظام متابعة المستخلصات والإشراف عليها — مجموعة الذيابي
## وثيقة المواصفات الكاملة (Specification)

> هذه الوثيقة موجهة لتنفيذ المشروع عبر Claude Code المتصل بـ GitHub و Supabase.
> اقرأها كاملة قبل البدء، ثم نفّذ ملفات SQL بالترتيب، انشر الـ Edge Function، وابنِ الواجهة.

---

## 1. نظرة عامة

نظام ويب لمتابعة المستخلصات المالية الصادرة من عدة إدارات، وتحويلها إلى إدارة الحسابات
لإصدار فواتير لها، مع دورة مراجعة وإرجاع وإشعارات فورية.

**الإدارات المشمولة:** التشغيل والصيانة، النقليات، الطرق، تأجير المعدات.
**الجهة المستقبِلة:** إدارة الحسابات.

النظام **منفصل تماماً** عن نظام "طلبات الصرف" الحالي (مشروع Supabase وريبو GitHub مستقلان)،
لكنه يحافظ على نفس الهوية البصرية (خط Cairo، الألوان الذهبية للمجموعة).

---

## 2. المكدّس التقني (Stack)

| الطبقة | التقنية |
|---|---|
| الواجهة | صفحة HTML واحدة + JavaScript صرف (بدون إطار) + خط Cairo |
| قاعدة البيانات | Supabase PostgreSQL |
| المصادقة | Supabase Auth (بريد داخلي مخفي خلف اسم مستخدم) |
| التخزين | Supabase Storage — bucket خاص `extract-files` مع Signed URLs |
| اللحظية | Supabase Realtime (اشتراك على جدول `extracts` و`notifications`) |
| قراءة Excel | مكتبة SheetJS (xlsx) عبر CDN |
| إنشاء المستخدمين | Supabase Edge Function `create-user` |
| الاستضافة | GitHub Pages (أو أي استضافة ثابتة) |

---

## 3. دورة العمل (Workflow)

الدورة **ثابتة** من أي إدارة إلى الحسابات، ومن الحسابات إلى أي إدارة:

```
الإدارة تسجل مستخلص + مرفقات
        ↓ (إرسال مباشر، بدون اعتماد داخلي)
   قيد المراجعة (pending_review)   ← عند الحسابات
        ↓ مراجعة الحسابات
   ┌────────────────┬─────────────────────┐
   ↓                                        ↓
مرتجع (returned)                    قيد التنفيذ (in_progress)
مع تعليق النواقص                     الحسابات تجهّز الفاتورة
   ↓                                        ↓
الإدارة تعدّل وترفع تاني            مكتمل (completed)
   ↑──── يرجع لـ pending_review        بعد رفع الفاتورة
```

**قواعد الانتقال بين الحالات:**
- `pending_review → in_progress` : الحسابات تقبل المستخلص للبدء في الفاتورة.
- `pending_review → returned`    : الحسابات ترجعه لنواقص (إلزامي كتابة `return_comment`).
- `returned → pending_review`    : الإدارة تعدّل المرفقات وتعيد الإرسال.
- `in_progress → completed`      : الحسابات ترفع الفاتورة (رقم يدوي + مبلغ + ملف اختياري).

---

## 4. الأدوار (Roles)

| الدور | القيمة | الصلاحيات |
|---|---|---|
| موظف إدارة | `department` | تسجيل مستخلص لإدارته، إرفاق ملفات، رؤية مستخلصات إدارته فقط، إعادة إرسال المرتجع |
| موظف حسابات | `accounts` | رؤية كل المستخلصات، المراجعة، الإرجاع بتعليق، رفع الفاتورة |
| أدمن | `admin` | كل ما سبق + إدارة المستخدمين + إدارة الإدارات + التقارير |

الحماية مفروضة على مستوى قاعدة البيانات عبر **RLS** (ملف `03_rls_policies.sql`)،
فحتى لو تلاعب أحد بكود الواجهة لا يستطيع رؤية بيانات إدارة أخرى.

---

## 5. القرارات المثبّتة (Confirmed decisions)

1. **فاتورة واحدة لكل مستخلص** — قيد `UNIQUE` على `invoices.extract_id`.
2. **بدون اعتماد داخلي** — الإرسال مباشر من الموظف إلى الحسابات.
3. **نظام منفصل تماماً** — مشروع Supabase وريبو GitHub مستقلان.
4. **المشاريع تُستورد من Excel** — لكل إدارة شيت مشاريعها، وتظهر كقائمة منسدلة عند إنشاء مستخلص.
5. **المستخدمون يُنشأون من شاشة الأدمن** — اسم مستخدم + كلمة مرور، عبر Edge Function.

## 6. الافتراضات (قابلة للتعديل)

- **ترقيم المستخلص:** تلقائي `CODE-YYYY-NNN` (مثل `OPS-2026-014`)، تسلسل مستقل لكل إدارة/سنة.
- **رقم الفاتورة:** يدوي من موظف الحسابات (رقم رسمي من نظامهم المحاسبي).
- **تصنيف المرفقات:** يوجد حقل `doc_type` (المستخلص / شهادة استلام / كشف كميات / أخرى)، افتراضي "أخرى".
- **شيت المشاريع لكل إدارة على حدة** (لا يوجد شيت عام مجمّع).

## 7. جداول قاعدة البيانات (ملخص)

| الجدول | الغرض |
|---|---|
| `departments` | الإدارات الأربعة (name, code) |
| `profiles` | المستخدمون وأدوارهم وإداراتهم (مرتبط بـ auth.users) |
| `projects` | مشاريع كل إدارة، تُستورد من Excel |
| `extracts` | السجل الرئيسي للمستخلصات وحالاتها |
| `attachments` | مرفقات كل مستخلص (في bucket خاص) |
| `invoices` | فاتورة واحدة لكل مستخلص |
| `extract_history` | سجل كامل للحركات (Audit Trail / Timeline) |
| `notifications` | الإشعارات الفورية |

التفاصيل الكاملة للأعمدة في `database/01_schema.sql`.

## 8. الشاشات المطلوبة

### 8.1 تسجيل الدخول
- إدخال اسم مستخدم + كلمة مرور.
- الواجهة تضيف الدومين الداخلي تلقائياً: `username@INTERNAL_EMAIL_DOMAIN` قبل استدعاء
  `sb.auth.signInWithPassword`. الموظف لا يرى أي بريد.

### 8.2 لوحة موظف الإدارة
- زر **"مستخلص جديد"** يفتح نموذج: المشروع (قائمة منسدلة)، الفترة (شهر/سنة)،
  قيمة المستخلص، ملاحظات، مرفقات متعددة (مع اختيار `doc_type` لكل ملف).
- جدول بمستخلصات إدارته: رقم المستخلص، المشروع، الفترة، المبلغ، الحالة (شارة ملونة)، التاريخ.
- عند حالة **مرتجع**: يظهر تعليق الحسابات + زر "تعديل وإعادة إرسال" (يضيف مرفقات ويعيد الحالة لـ pending_review).

### 8.3 لوحة موظف الحسابات
- جدول بكل المستخلصات من كل الإدارات، مع فلاتر: الإدارة، الحالة، الشهر.
- عدّادات علوية: قيد المراجعة / قيد التنفيذ / مرتجع / مكتمل.
- فتح المستخلص يظهر التفاصيل + المرفقات (روابط Signed URL) + الأزرار:
  - **قبول للتنفيذ** (pending_review → in_progress)
  - **إرجاع مع ملاحظة** (يفتح حقل تعليق إلزامي → returned)
  - **رفع الفاتورة** (in_progress → completed): رقم الفاتورة + المبلغ + ملف اختياري.

### 8.4 شاشة تفاصيل المستخلص (للطرفين)
- Timeline من `extract_history` يعرض كل الحركات بالترتيب مع التعليقات والتواريخ والفاعل.
- قائمة المرفقات مع أنواعها وروابط التحميل المؤقتة.

### 8.5 شاشة الأدمن — إدارة المستخدمين
- فورم: اسم الموظف، اسم مستخدم، كلمة مرور، الدور، الإدارة (لو الدور department).
- يستدعي Edge Function `create-user`.
- جدول بالمستخدمين الحاليين مع إمكانية التعطيل (is_active).

### 8.6 شاشة استيراد المشاريع
- رفع ملف Excel، قراءته بـ SheetJS، معاينة الصفوف، ثم إدراج دفعة واحدة في `projects`.
- الأعمدة المتوقعة في الشيت: `name` (إلزامي)، `code` (اختياري).
- للأدمن: يختار الإدارة. لموظف الإدارة: يُستورد لإدارته تلقائياً.

### 8.7 التقارير / التصدير
- تصدير Excel لقائمة المستخلصات المفلترة (زر مثل الموجود في نظام طلبات الصرف الحالي).

## 9. الإشعارات (Realtime)

- عند **INSERT** على `extracts` → إشعار لكل الحسابات (`target_role='accounts'`).
- عند التحويل إلى **returned** → إشعار لإدارة المستخلص (`target_dept`).
- عند **resubmit** (returned→pending_review) → إشعار للحسابات.
- عند **completed** → إشعار لإدارة المستخلص.

كل هذا يتم تلقائياً بمشغّلات قاعدة البيانات (ملف `02_functions_triggers.sql`)،
فالواجهة فقط **تشترك** عبر Realtime على جدول `notifications` وتعرض جرساً بعدّاد غير المقروء.

مثال اشتراك في الواجهة:
```js
sb.channel('notif')
  .on('postgres_changes',
      { event: 'INSERT', schema: 'public', table: 'notifications' },
      payload => refreshNotifications())
  .subscribe();
```

## 10. خطوات التنفيذ لـ Claude Code

1. أنشئ مشروع Supabase جديداً (منفصل) واحفظ `SUPABASE_URL` و`anon key`.
2. في SQL Editor، نفّذ الملفات بالترتيب:
   `01_schema.sql` → `02_functions_triggers.sql` → `03_rls_policies.sql` → `04_seed_storage.sql`.
3. أنشئ أول مستخدم أدمن من Supabase Auth ثم أضف صفه في `profiles` (انظر تعليق نهاية `04`).
4. اضبط أسرار الـ Edge Function: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `INTERNAL_EMAIL_DOMAIN`.
5. انشر الدالة: `supabase functions deploy create-user`.
6. ابنِ `index.html` وفق الشاشات في القسم 8، وضع فيه `SUPABASE_URL` و`anon key` فقط
   (لا تضع service role key أبداً في الواجهة).
7. ارفع على GitHub وفعّل GitHub Pages.

---

## 11. ملاحظات أمنية مهمة

- **service role key** يبقى فقط في أسرار الـ Edge Function — لا يظهر إطلاقاً في كود الواجهة.
- المرفقات في bucket **خاص** (غير عام)؛ الوصول عبر Signed URLs قصيرة العمر فقط.
- RLS مفعّل على كل الجداول؛ لا تعطّله. أي منطق حماية إضافي في الواجهة هو طبقة تجميل فقط،
  الحماية الحقيقية في قاعدة البيانات.
- `return_comment` إلزامي في الواجهة عند الإرجاع (لضمان توضيح سبب النواقص للإدارة).
